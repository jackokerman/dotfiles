# Priority Order

Resolve the category label and matching active top-level smart list dynamically. Read incomplete Next Actions and Someday tasks through `godspeed` so wire-level `list_ordinals` remain available, then filter to top-level tasks carrying the label.

Never emit the raw source-list task responses into context. Stream each response directly through a JSON filter. The ranking pass should project only labeled top-level roots and the fields needed to rank them: `id`, `title`, `list_id`, `created_at`, and the matching smart-list ordinal. After selecting the root, fetch its notes with `task get`; then make a filtered source-list pass sorted by numeric `order_index` to retain only that root and its following descendants up to the next top-level task. Fetch the selected child's full notes with `task get`. Do not rely on API response order as persisted source-list order.

If any matching root has an ordinal for the smart-list ID, roots with explicit ordinals rank first by that ordinal and implicit roots follow by creation time. Compare ordinals as base-62 numbers using Godspeed's digit order `0-9`, `a-z`, then `A-Z`; ordinary locale or ASCII string ordering is incorrect. If none has an ordinal, rank all matching roots by creation time. Nested descendants stay attached to their root and never outrank it. Do not infer priority from title, due date, source-list order, or task recency when smart-list order exists.

For a repository or domain request with no matching category label and smart list, use a bounded fallback instead of dumping the source lists. Filter each response before output to top-level tasks whose title or notes explicitly mention the supplied repository or domain, and project only `id`, `title`, `list_id`, `created_at`, and `order_index`. Treat a repository name embedded in another repository basename, such as `dotfiles` inside `other-dotfiles`, as a different repository unless an exact path proves otherwise. Rank Next Actions ahead of Someday and then by numeric `order_index`; fetch full notes only for the selected task. State that this is source-list priority without a category ordinal. Do not widen the match semantically or emit unrelated tasks.

For repository next-work requests, compare the selected root's stated outcome with bounded current-repository evidence before returning it as actionable. If that evidence proves the outcome is already satisfied, identify the task as stale, continue to the next ranked candidate, and do not complete or clear anything without approval.
